Rate Limiting Design Note

Summary

We propose per-key token-bucket limits on the public REST API, enforced at the gateway, with clear headers so clients can back off gracefully.

Problem

Our public REST API has no request limits. A handful of integrations account for most load spikes, and a single misbehaving client degraded p99 latency for everyone twice last quarter.

Who is affected

Every API customer during a spike; on-call engineers, who currently mitigate by hand-editing firewall rules.

What we've tried

Manual IP blocks and asking customers to slow down. Neither scales, and blocks catch shared NAT addresses.

Goals

Protect shared capacity, give clients predictable limits, and make limit changes a config edit rather than a deploy.

Design

Token buckets per API key

Each key gets a bucket with a refill rate and burst size taken from its plan. Buckets live in Redis with a Lua script for atomic take-and-refill.

Response headers

Every response carries RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset; throttled requests return 429 with Retry-After.

Failure modes

If Redis is unreachable the gateway fails open with a local in-memory bucket, so an outage in the limiter never becomes an API outage.

Alternatives considered

Fixed windows are simpler. Fixed one-minute windows are simpler to explain but allow 2× bursts at window edges; we measured this pattern in 3 of our top 10 integrations.

Sliding window log

Exact, but stores one entry per request — roughly 40 GB of Redis at current peak. Rejected on cost.

Leaky bucket

Smooths traffic well but adds queueing latency, which our synchronous clients handle poorly.

Rollout

We will roll out in three phases over six weeks, starting with internal keys, then a shadow mode that only logs, and finally enforcement for all keys. Internal keys → shadow mode (log only) → enforce, over six weeks.

Communication

Email to all key owners two weeks before enforcement, plus a changelog entry and docs for the new headers.

Open questions

Should burst size scale with plan tier, or stay flat? Do we need per-endpoint limits for the search API?
